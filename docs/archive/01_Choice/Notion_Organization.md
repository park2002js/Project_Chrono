# Notion 기획 정리 방식과 개발 착수 순서

주제: 2026-11-14 사용자가 제공한 Notion 기획을 클래스 정의·케이스 구현 흐름·고민/결정으로 통합함.
- 원문은 `/docs/notes/notion 문서`에 보존하고, 현재 사양은 [GAME_SPEC](../../GAME_SPEC.md), 답변 대기는 [QUESTIONS](../../QUESTIONS.md)에 관리함.
- [Notion 정리 페이지](https://app.notion.com/p/41857a6d6d24809a8d15f1a5aa34d48a)에 검토용 게시본을 작성함. 자동 동기화는 아님.

# 선택 사안 1 — 정의를 먼저 정리

- 선택: 모든 Case가 요구하는 역할의 누락을 보완한 뒤, 각 class/struct/enum을 역할·생명 주기·공개 API·공개 변수·연관 class로 정리함. 카테고리는 Player, Boss, UI/anim, 시스템/기타.
- 이유: 추후 Class Diagram의 기반으로 사용하기 위함.
- 제시된 다른 선택 사안들: 없음. 사용자가 직접 지정함.

# 선택 사안 2 — 이름과 부족한 정보의 사용자 결정

- 선택: 원문에 정의되지 않은 API·변수 이름은 역할별 후보를 보여주고 사용자가 결정함. 수명·관계는 원문을 최대한 정리한 뒤 채우지 못한 부분만 질문함.
- 이유: 원문을 살리고 사용자가 역할별 이름을 정의하기 위함.
- 제시된 다른 선택 사안들: 없음. 보완 후보는 GAME_SPEC에 제안으로 표시하며 아직 채택하지 않음.

# 선택 사안 3 — 케이스 흐름과 실제 구현의 동시 작성

- 선택: 1장 정의 완료 뒤 2장 상세 흐름을 실제 코드 작성과 함께 진행. 동시는 `+`, 선행 완료 후 시작은 `→`, 분기는 `if : 조건` 하위 목록.
- 이유: 사용자가 해당 흐름이 제대로 구현되는지 확인하기 위함.
- 제시된 다른 선택 사안들: 코드 없이 흐름만 완료시키는 방식은 이번 요청에 해당하지 않음.

# 선택 사안 4 — 개발 착수와 연출의 경계

- 선택: 문서 작업이 완전히 끝나고 Sprite·FX·animation 등의 연출을 제외한 로직 방향이 확실해진 뒤 Unity 개발 시작. 연출은 완전히 정의되면 구체 구현하되 필요한 코드 계약부터 준비.
- 이유: 개발 착수 순서에 대한 별도 이유 미기록. 사용자의 후속 답변을 그대로 반영함.
- 제시된 다른 선택 사안들: 없음. Unity 프로젝트 경로를 찾거나 지금 생성하는 것으로 이어가지 않음.

# 선택 사안 5 — 고민과 선택 이유 보존

- 선택: 비교·성능 고민은 GAME_SPEC 3.1, 원문 선택과 이유는 3.2에 모음. UniTask·FMOD와 필요한 최소 도구는 공식 호환/비용 근거로 비교.
- 이유: 산발적으로 적힌 비교 과제와 선택 이유를 잊지 않고 후속 검증·보고서에 쓰기 위함.
- 제시된 다른 선택 사안들: 도구 후보 조사만으로 설치·구매·Unity 버전을 변경하지 않음. Q21~23 답변 대기.
