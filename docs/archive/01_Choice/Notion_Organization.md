# Notion 기획 정리 방식과 개발 착수 순서

주제: 2026-11-14 사용자가 제공한 Notion 기획을 클래스 정의·케이스 구현 흐름·고민/결정으로 통합함.
- 원문은 `/docs/notes/notion 문서`에 보존하고, 현재 사양은 [GAME_SPEC](../../GAME_SPEC.md), 답변 대기는 [QUESTIONS](../../QUESTIONS.md)에 관리함.
- [Notion 정리 페이지](https://app.notion.com/p/41857a6d6d24809a8d15f1a5aa34d48a)에 검토용 게시본을 작성함. 자동 동기화는 아님.

# 선택 사안 1 — 정의를 먼저 정리

- 선택: 모든 Case가 요구하는 역할의 누락을 보완한 뒤, 각 class/struct/enum을 역할·생명 주기·공개 API·공개 변수·연관 class로 정리함. 카테고리는 Player, Boss, UI/anim, 시스템/기타.
- 이유: 추후 Class Diagram의 기반으로 사용하기 위함.
- 제시된 다른 선택 사안들: 없음. 사용자가 직접 지정함.

# 선택 사안 2 — 이름과 부족한 정보의 사용자 결정

- 선택: 원문에 정의되지 않은 API·변수 이름은 역할별 후보를 보여주고 사용자가 결정함. 수명·관계는 원문을 최대한 정리한 뒤 채우지 못한 부분만 질문함.
- 이유: 원문을 살리고 사용자가 역할별 이름을 정의하기 위함.
- 제시된 다른 선택 사안들: 없음. 보완 후보는 GAME_SPEC에 제안으로 표시하며 아직 채택하지 않음.

# 선택 사안 3 — 케이스 흐름과 실제 구현의 동시 작성

- 선택: 1장 정의 완료 뒤 2장 상세 흐름을 실제 코드 작성과 함께 진행. 동시는 `+`, 선행 완료 후 시작은 `→`, 분기는 `if : 조건` 하위 목록.
- 이유: 사용자가 해당 흐름이 제대로 구현되는지 확인하기 위함.
- 제시된 다른 선택 사안들: 코드 없이 흐름만 완료시키는 방식은 이번 요청에 해당하지 않음.

# 선택 사안 4 — 개발 착수와 연출의 경계

- 선택: 문서 작업이 완전히 끝나고 Sprite·FX·animation 등의 연출을 제외한 로직 방향이 확실해진 뒤 Unity 개발 시작. 연출은 완전히 정의되면 구체 구현하되 필요한 코드 계약부터 준비.
- 이유: 개발 착수 순서에 대한 별도 이유 미기록. 사용자의 후속 답변을 그대로 반영함.
- 제시된 다른 선택 사안들: 없음. Unity 프로젝트 경로를 찾거나 지금 생성하는 것으로 이어가지 않음.

# 선택 사안 5 — 고민과 선택 이유 보존

- 선택: 비교·성능 고민은 GAME_SPEC 3.1, 원문 선택과 이유는 3.2에 모음. UniTask·FMOD와 필요한 최소 도구는 공식 호환/비용 근거로 비교.
- 이유: 산발적으로 적힌 비교 과제와 선택 이유를 잊지 않고 후속 검증·보고서에 쓰기 위함.
- 제시된 다른 선택 사안들: 도구 후보 조사만으로 설치·구매·Unity 버전을 변경하지 않음. Q21~23 답변 대기.

# 최초 정리 당시 반영의 한계

- 원문 통합 초안과 23개 질문 주제, Notion 연결·페이지 작성까지 수행함. 개별 게임 사양·API 후보 선택, 프로젝트 생성, 구현·Unity 컴파일·플레이·성능 비교는 수행하지 않음.
- 38개 Boss 패턴은 누락 방지를 위해 보존한 목록이며 제출 범위 확정이 아님. 1장 정의 완료/2장 구현 완료로 표시하지 않음.

# 선택 사안 6 — 코드 작업과 Sequence Diagram 저장의 동시 수행

- 선택: 2026-11-15 후속 요청부터 코드 작업마다 Notion 정리2장의 해당 기능 표 아래에 `Sequence Diagram` 토글을 두고, `기능 ID 제목 → 번호가 붙은 Case → 설명 → Mermaid 코드 블록` 순서로 해당 흐름을 함께 저장함. 실제 사용자 예시는 시스템 표 아래 토글의 F-S01·① 게임 실행→Title 준비임.
- 이유: 별도 이유 미기록. 사용자가 이후 코드 작업의 기본 행동방침으로 직접 지정함.
- 제시된 다른 선택 사안들: 없음. 현재 예시 형식을 보존해 적용함.
- 이번 적용: 사용자가 미리 쓴①은 보존하고 같은 F-S01 아래②~⑥의 설명·Mermaid5개를 추가함.④ 저장·⑥ 종료 대기는 F-S02 공통 저장 도구와 연결된 범위로 표시함. 미구현 기능이나 미검증 종료 동작을 완료로 바꾸지 않음.
- 승인 범위: 이후 요청한 코드 작업에 대응하는 이 위치의 기록·갱신은 반복 승인 없이 수행함. 백그라운드 자동 동기화나 다른 Notion 페이지·무관한 변경에 대한 승인은 아님. 절차 원본은 AGENTS의 Unity 코드 작업과 DESIGN의 Sequence Diagram 작성 기준을 따름.

# 선택 사안 7 — 기능별 독립 토글과 다이어그램 미리보기

- 선택: 2026-11-15 후속 요청으로 토글 제목을 `F-S01 SequenceDiagram`, `F-P01 SequenceDiagram`처럼 기능 ID부터 시작하고 기능마다 독립 토글을 둠. 안쪽의 중복 기능 제목을 제거하며 번호Case·설명·Mermaid를 유지함. Mermaid는 병행 대신 미리보기로 표시함.
- 이유: 기존 문서가 너무 길어 기능마다 접어서 확인하기 위함. 다이어그램 미리보기 선택의 별도 이유는 미기록이며 사용자가 직접 지정함.
- 제시된 다른 선택 사안들: 기존 공통 토글 안의 기능 제목과 코드·다이어그램 병행 표시를 이번 요청으로 변경함.
- 이번 적용: F-S01의6개 Case를 보존하고 F-P01 구현 후3개 Case를 별도 토글에 저장함. Notion 앱에서 총9개 다이어그램의 미리보기 표시·코드 숨김을 확인함. AGENTS·DESIGN·STATUS·PLANS를 갱신했으며 F-P01의 구현/검증 원본은 GAME_SPEC 2.1.1임.

# 선택 사안 8 — 미리보기 설정·확인을 작업 절차에서 제외

- 선택: 2026-11-15 최신 요청으로 Notion Mermaid 미리보기 표시 모드 설정·화면 확인을 작업 및 완료 체크에서 제외한다. 이를 위해 마우스·브라우저 UI를 조작하지 않으며 기존 미리보기 확인 미완 과제도 제거한다.
- 이유: 미리보기만을 위한 컴퓨터 마우스 조작에 드는 시간이 낭비라는 사용자 판단.
- 유지 범위: 기능별 독립 토글·번호Case·설명·Mermaid 내용 저장과 연결 도구의 저장 결과 확인. 주석만 바뀌어 호출 흐름이 같으면 시퀀스를 다시 만들지 않는다.
- 대체 관계: 선택 사안7의 기능별 토글 형식은 유지하며 미리보기 설정·확인 의무만 이번 요청으로 대체한다. 과거 실제 확인 이력은 그대로 보존한다.
